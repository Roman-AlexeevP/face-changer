# Requirements: Face Changer

**Defined:** 2026-11-08
**Core Value:** пользователь за одно сообщение с фото получает правдоподобное
видео со своим лицом; путь «фото → оплата → видео → доставка» работает даже
если всё остальное сломается.

## v1 Requirements

### Entry & Consent

- [ ] **ENTRY-01**: Первый `/start` создаёт пользователя и показывает экран
  согласия без кнопки оплаты.
- [ ] **ENTRY-02**: Экран согласия содержит: 18+, только своё лицо, запрет
  чужих фото и несовершеннолетних, ответственность за согласие третьих лиц,
  передачу фото внешнему сервису Higgsfield, удаление фото после генерации,
  отсутствие хранения результата (только `file_id`).
- [ ] **ENTRY-03**: Нажатие «Принимаю» записывает `consent_version`,
  `consent_at` и событие `consent_given`; без согласия фото не принимается.
- [ ] **ENTRY-04**: Изменение текста согласия повышает версию и требует нового
  согласия; старая версия не считается действующей.
- [ ] **ENTRY-05**: Повторный `/start` после согласия показывает домашний экран
  с кнопкой оплаты, а не экран согласия.
- [ ] **ENTRY-06**: Принимается `photo` или `image/*` документ ≤ 20 МБ,
  сторона ≤ 4096 px, форматы JPEG/PNG/WEBP; иное — вежливый отказ без списания.
- [ ] **ENTRY-07**: Текст, стикер, видео и не-фото документ не создают заказ;
  бот просит фото. Вне состояния `paid` текст получает подсказку, а не
  требование фото.
- [ ] **ENTRY-08**: Пока есть активный заказ (`paid`, `queued`, `running`),
  новый заказ не создаётся; бот показывает статус текущего.
- [ ] **ENTRY-09**: «Ещё раз» после `delivered` создаёт новый оплаченный заказ
  и просит новое фото; старое фото не переиспользуется. Бесплатного реролла в
  v1 нет.

### Template Catalog

- [ ] **TMPL-01**: Шаблон хранится в БД и в `templates/<key>/config.yaml`:
  `key`, `title`, `prompt`, `engine_model`, `duration_sec`, `resolution`,
  `credits_cost`, `price_kopecks`, `is_active`, `is_default`.
- [ ] **TMPL-02**: При старте процесса `config.yaml` синхронизируется с
  таблицей; правка промпта подхватывается рестартом без изменения кода.
- [ ] **TMPL-03**: Ровно один активный шаблон помечен `is_default`; два
  default — ошибка конфигурации; ни одного — «технические работы» и алерт.
- [ ] **TMPL-04**: Промпт не показывается пользователю и не принимается от
  пользователя.
- [ ] **TMPL-05**: Перед оплатой пользователь видит превью шаблона, цену и
  длительность.
- [ ] **TMPL-06**: `source.mp4` загружается в движок один раз; URL кэшируется
  в `templates.engine_video_url` с отметкой времени и TTL. При ошибке доступа
  к видео — одна перезагрузка ассета и повтор.

### Generation

- [ ] **GEN-01**: Система не удерживает HTTP-запрос пользователя на время
  генерации; заказ ставится в очередь, создаётся `job(status=new)`,
  пользователь сразу получает подтверждение.
- [ ] **GEN-02**: `idempotency_key = "<order_id>:<attempt>"`, `UNIQUE` в БД;
  повторный submit с тем же ключом не создаёт вторую генерацию.
- [ ] **GEN-03**: `jobs.request_id` записывается сразу после submit; при
  наличии `request_id` воркер продолжает polling, а не делает новый submit.
- [ ] **GEN-04**: Polling идёт с интервалом 2–10 секунд и прекращается при
  терминальном статусе, таймауте или исчерпании неизвестных статусов.
- [ ] **GEN-05**: При превышении `JOB_TIMEOUT_MIN` задание переходит в
  `failed` с кодом `timeout`, кредит возвращается.
- [ ] **GEN-06**: Повторяемые ошибки (сеть, 5xx, `failed` движка) повторяются
  не более 3 раз после первой попытки (всего 4) с backoff 2/5/15 секунд;
  каждая попытка увеличивает `attempt`, получает новый ключ и
  `next_attempt_at`.
- [ ] **GEN-07**: Отказ модерации (`nsfw`) не повторяется; заказ переходит в
  `rejected`, кредит возвращается, пользователь получает объяснение.
- [ ] **GEN-08**: Ошибка «нет кредитов» (HTTP 402) переводит заказ в `failed`
  с кодом `no_credits`, возвращает кредит, ставит паузу продаж на 60 минут и
  шлёт алерт админу.
- [ ] **GEN-09**: Ответы движка нормализуются в коды `timeout`, `moderated`,
  `no_credits`, `engine_5xx`, `network`, `bad_input`, `unknown`; внутренние
  `engine_auth`, `engine_bad_config`, `rate_limited` не показываются
  пользователю. Наружу — только человеческий текст.
- [ ] **GEN-10**: Неразобранный ответ даёт код `unknown`; санитизированный
  сырой ответ сохраняется в `events.props` и логах, пользователю — нейтральный
  текст.
- [ ] **GEN-11**: Сторож возвращает в очередь задания, висящие в `running`
  дольше `JOB_STALE_MINUTES`: `job → new` с инкрементом `attempt`, заказ
  `running → queued`.
- [ ] **GEN-12**: Контракт Higgsfield подтверждён живыми запросами: auth,
  upload, submit, `status_url`, имена статусов, `video.url`, форма ошибок,
  время генерации и расход кредитов. Неподтверждённых полей в используемом
  пути нет; `docs/higgsfield-contract.md` обновлён.

#### Матрица ошибок движка

| Исход | Код | Повтор задания | Статус заказа | Ledger | Пользователь |
|---|---|---|---|---|---|
| `completed` + `video.url` | — | — | `delivered` | `topup` + `order_paid`, без refund | видео |
| `failed`, повторяемая причина | `engine_failed` | да, 3 повтора | retry; после исчерпания `failed` | `refund` | общий текст |
| `failed`, неповторяемая | `engine_failed` | нет | `failed` | `refund` | общий текст |
| `nsfw` | `moderated` | нет | `rejected` → `refunded` | `refund` | «фото не прошло модерацию» |
| HTTP 402 | `no_credits` | нет | `failed` + код | `refund`, пауза продаж 60 мин, алерт | «технические работы» |
| HTTP 401/403 | `engine_auth` (внутр.) | нет | `failed` | `refund` | общий текст |
| HTTP 400/422 | `bad_input` | нет | `failed` | `refund` | общий текст |
| HTTP 404 | `engine_bad_config` (внутр.) | нет | `failed` | `refund` | общий текст |
| HTTP 429 | `rate_limited` (внутр.) | да, с `Retry-After` | retry | — | — |
| HTTP 5xx после 3 HTTP-попыток | `engine_5xx` | да, job retry | `failed` после исчерпания | `refund` | общий текст |
| сеть после 3 HTTP-попыток | `network` | да, job retry | `failed` после исчерпания | `refund` | общий текст |
| polling timeout | `timeout` | нет | `failed` | `refund` | «не успели» |
| неизвестный статус ×4 | `unknown` | нет | `failed` | `refund` | общий текст |
| битый ответ | `unknown` | нет | `failed` | `refund` | общий текст |

Правила: транспорт повторяет отдельный HTTP-запрос до 3 раз; задание
повторяется отдельно и не более 3 раз. `moderated`, `no_credits`, `bad_input`,
`engine_auth`, `engine_bad_config`, `unknown` не повторяются. Повторный
`refund` по одному заказу невозможен.

### Billing & Ledger

- [ ] **BILL-01**: Заказ создаётся до фото; фото запрашивается только после
  `order(status=paid)`.
- [ ] **BILL-02**: `PaymentProvider=stub` мгновенно переводит заказ в `paid`,
  создаёт записи ledger и событие `order_paid`; код хендлера не зависит от
  провайдера.
- [ ] **BILL-03**: Баланс меняется только записями ledger; причины —
  `topup`, `order_paid`, `refund`; баланс = сумма `delta`; прямых апдейтов
  баланса нет.
- [ ] **BILL-04**: `topup` пополняет баланс на целое число кредитов; для
  оплаты деньгами — на `credits_cost` заказа; ручная корректировка админа
  может быть отрицательной, но только с аудитом старого и нового баланса.
- [ ] **BILL-05**: `order_paid` создаётся ровно один раз на заказ,
  `delta = -credits_cost`; повторная оплата не списывает дважды.
- [ ] **BILL-06**: `refund` создаётся ровно один раз, только для `failed` или
  `rejected`, `delta = +credits_cost`; для `delivered` возврат невозможен;
  повторный возврат отклоняется.
- [ ] **BILL-07**: Повторное событие оплаты с тем же `payment_id`
  игнорируется: баланс не меняется, в лог пишется предупреждение.
- [ ] **BILL-08**: Один активный заказ на пользователя; в БД есть частичный
  уникальный индекс на `orders(user_id)` для `paid/queued/running`.
- [ ] **BILL-09**: `price_kopecks` и `credits_cost` фиксируются в заказе в
  момент создания; изменение тарифа не влияет на старые заказы.
- [ ] **BILL-10**: Возвраты только кредитами; автоматических денежных
  возвратов нет. Деньги возвращаются вручную по обращению, обращение
  фиксируется в `events`.

#### Правила ledger

1. Записи только добавляются; обновление и удаление запрещены.
2. `topup` — приход кредитов (оплата деньгами или ручная корректировка).
3. `order_paid` — расход кредитов на конкретный заказ, ровно один раз.
4. `refund` — возврат кредитов за `failed`/`rejected`, ровно один раз.
5. Баланс не хранится отдельным полем; он считается суммой записей.
6. Отрицательный баланс невозможен: гейт проверяет остаток до создания заказа.
7. Деньги — копейки, кредиты — целые; `float` в деньгах запрещён.

### Delivery

- [ ] **DELIV-01**: Результат отправляется как `video`, а не документ, если
  размер ≤ 20 МБ.
- [ ] **DELIV-02**: Результат нормализуется в H.264, 720p, 30 fps, AAC,
  `faststart`; `webm` и иные контейнеры конвертируются перед отправкой.
- [ ] **DELIV-03**: Если после нормализации файл больше лимита — отправка
  документом; заказ не считается проваленным.
- [ ] **DELIV-04**: `file_id` сохраняется в `orders`; повторная доставка
  использует `file_id`, а не перегенерацию.
- [ ] **DELIV-05**: При 429 отправка повторяется после `retry_after`; заказ не
  переходит в `failed` из-за лимита Telegram.
- [ ] **DELIV-06**: Видео по одному заказу не отправляется дважды; при
  `orders.status=delivered` отправка пропускается.
- [ ] **DELIV-07**: Локальная копия результата удаляется после успешной
  отправки; в БД остаются `file_id` и метаданные.

### Privacy & Retention

- [ ] **PRIV-01**: Исходное фото удаляется при любом терминальном статусе:
  `delivered`, `failed`, `rejected`, `refunded`, `purged`.
- [ ] **PRIV-02**: Если постановка в очередь провалилась, сохранённое фото
  удаляется в том же обработчике.
- [ ] **PRIV-03**: Сторож удаляет фото через 15 минут после загрузки
  независимо от статуса задания.
- [ ] **PRIV-04**: `STORAGE_DIR` очищается при старте процесса; временные
  каталоги не переживают перезапуск контейнера.
- [ ] **PRIV-05**: В логах нет фото, имени, `tg_id` в открытом виде,
  подписанных URL и сырых Telegram-объектов; только `order_id`, `job_id`,
  статусы и коды ошибок.
- [ ] **PRIV-06**: В `users` хранятся `consent_version` и `consent_at`, достаточные
  для подтверждения правомерности обработки.
- [ ] **PRIV-07**: По запросу пользователя удаляются фото, временные файлы и
  связанные артефакты; остаются только агрегированные события без
  идентификаторов.
- [ ] **PRIV-08**: Файлы доступны только по подписанной ссылке с TTL ≤ 15
  минут; публичного листинга каталога нет. Для локального диска — только
  внутренний путь без публичного URL.

#### Удаление фото

| Событие | Что удаляется | Когда |
|---|---|---|
| `delivered` | `photo-<order_id>.jpg` | сразу после успешной отправки |
| `failed` | фото | сразу при терминальном статусе |
| `rejected` | фото | сразу при терминальном статусе |
| `refunded` | остатки фото | сразу при переходе |
| зависшее задание | фото | не позднее 15 минут с загрузки |
| провал очереди | фото | в обработчике ошибки |
| рестарт | осиротевшие файлы | при старте процесса |

### Operations

- [ ] **OPS-01**: `SALES_ENABLED=false` или сервисный флаг блокируют новые
  заказы; уже оплаченные заказы доводятся до конца.
- [ ] **OPS-02**: Гейт по кредитам не создаёт заказ, если доступного остатка
  меньше `credits_cost`; показывает «технические работы» и шлёт алерт
  `low_credits`.
- [ ] **OPS-03**: Дневной лимит генераций на пользователя; при превышении бот
  сообщает, когда вернуться, и не создаёт заказ.
- [ ] **OPS-04**: Админ-команды только для `TG_ADMIN_IDS`: `/admin stats`,
  `/admin balance <n>`, `/admin sales on|off`, `/admin ban <tg_id>`,
  `/admin order <id>`.
- [ ] **OPS-05**: Не-админ получает нейтральный отказ; попытка пишется в
  `events`.
- [ ] **OPS-06**: `/admin order <id>` показывает статусы, коды ошибок и
  `request_id`, но не само фото.
- [ ] **OPS-07**: Алерты админу: `low_credits`, `job_stale`, `no_credits`,
  доля ошибок за час > 20%.
- [ ] **OPS-08**: `/admin stats` показывает заказы за 24 часа, долю успешных,
  среднее время генерации, расход кредитов и время последнего успешного
  заказа; все админ-действия аудируются в `events`.
- [ ] **OPS-09**: `/health` возвращает 200 при доступной БД и 503 при
  недоступной, а также возраст последней обработанной задачи.

### Payments (ЮKassa)

- [ ] **PAY-01**: `PaymentProvider=yookassa` реализован и не падает
  `ConfigError`; `stub` не используется в проде.
- [ ] **PAY-02**: Создание счёта передаёт сумму в копейках, `order_id`,
  `idempotency_key` и возвращает `payment_id`.
- [ ] **PAY-03**: Подтверждение оплаты идемпотентно: повторное уведомление с
  тем же `payment_id` не меняет баланс.
- [ ] **PAY-04**: При успешной оплате создаются `topup` и `order_paid`, заказ
  переходит в `paid`, пользователь получает запрос фото.
- [ ] **PAY-05**: При отказе или отмене оплаты заказ не получает списание;
  пользователь видит понятный текст и может попробовать снова.
- [ ] **PAY-06**: Денежные возвраты — вручную; кредитный возврат — по
  правилам ledger. Автоматический денежный возврат запрещён.
- [ ] **PAY-07**: Чеки и фискализация соответствуют требованиям ЮKassa для
  самозанятого; секреты только в `.env`, не логируются и не коммитятся.

### Quality

- [ ] **QA-01**: E2E через aiogram test-client: `/start → согласие → stub-оплата
  → фото → mock-видео → delivered`, с проверкой ledger и удаления фото.
- [ ] **QA-02**: Тест «миграция == модели»: `alembic upgrade head` на пустой БД
  и сверка с `Base.metadata`.
- [ ] **QA-03**: Тесты пайплайна с фейковым движком и фейковым ботом: успех,
  `rejected`, `no_credits`, `timeout`, исчерпание повторов, ровно один refund,
  ошибка доставки.
- [ ] **QA-04**: CI на каждый пуш: ruff + pytest + покрытие; падение тестов
  блокирует merge.
- [ ] **QA-05**: Порог покрытия `--cov-fail-under` после появления
  интеграционных тестов; покрытие не ниже 62%.
- [ ] **QA-06**: Тест архитектуры: `app/domain/` не импортирует `aiogram`,
  `sqlalchemy`, `httpx`, `os`, `time`, `random`, `uuid`.
- [ ] **QA-07**: `docs/architecture.md` соответствует коду: `VideoEngine`,
  статусы job, отсутствие FastAPI, локальное хранилище.

## Out of Scope

| Feature | Reason |
|---|---|
| Бесплатный реролл в v1 | Проще MVP; сначала данные по качеству и экономике |
| Telegram WebApp | Не нужен для проверки гипотезы |
| История заказов и личный кабинет | Вне MVP |
| Пользовательские промпты | Промпт только из шаблона |
| Подписки и рекуррентные платежи | Вне MVP |
| S3/CDN, Redis, Celery | Локальный диск и PostgreSQL достаточны |
| Внешняя аналитика | События в БД на первом этапе |
| Мультиязычность | Рынок РФ, один язык |
| Реферальная программа | Вне MVP |
| Детекция лиц | Снято с объёма решением продукта |
| Автоматические денежные возвраты | Только кредиты; деньги вручную |
