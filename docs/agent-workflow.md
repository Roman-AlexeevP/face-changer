# Agent Workflow

Этот документ описывает воспроизводимый цикл работы агента в репозитории. Он
дополняет `AGENTS.md`: там находятся правила кода, здесь — порядок действий и
ожидаемые доказательства результата.

## 1. Начало задачи

Перед изменением кода агент читает в таком порядке:

1. `AGENTS.md` — обязательные правила проекта;
2. `.planning/PROJECT.md` — контекст и продуктовые границы;
3. `.planning/STATE.md` — текущая позиция и блокеры;
4. `.planning/ROADMAP.md` — активная фаза и критерии приёмки;
5. `.planning/REQUIREMENTS.md` — требования и их ID;
6. текущий `CONTEXT.md` или `PLAN.md` фазы;
7. только после этого — исходный код и тесты затронутого участка.

Если задача не связана с активной фазой, агент сначала объясняет расхождение и
не начинает реализацию по памяти.

## 2. Планирование

Для новой продуктовой работы порядок такой:

```text
требование с ID
  → критерий в ROADMAP
  → PLAN.md с конкретными файлами и проверками
  → реализация
```

План должен назвать:

- файлы, которые создаются или изменяются;
- интерфейсы и границы ответственности;
- тест, который доказывает каждую существенную часть;
- команду проверки и ожидаемый результат;
- внешние зависимости и условия остановки.

Для текущей Phase 2 сначала нужно пройти supporting requirements `REPO-01…03`,
затем получить доступы и выбрать платёжный маршрут до создания детального плана
live-интеграции.

## 3. Реализация

Агент придерживается цикла:

```text
прочитать → изменить минимально → проверить узко → проверить шире →
обновить planning → показать evidence
```

Границы проекта:

- доменная логика остаётся чистой и не импортирует инфраструктуру;
- внешние сервисы подключаются через `Protocol` и адаптеры;
- mock/stub не удаляются ради live-интеграции;
- секреты читаются только из `.env`/environment;
- credentials, фото, подписанные URL и PII не попадают в git и логи;
- агент не подменяет неизвестный внешний контракт предположением без probe;
- коммит создаётся только по явному запросу пользователя.

## 4. Проверки

### Быстрый mock demo

```powershell
.\tasks.cmd demo
```

Команда запускает mock E2E-сценарий в Docker с PostgreSQL и не требует
Telegram-токена, Higgsfield credentials, платёжных ключей или ручного SQL.

### Полный тестовый прогон

```powershell
.\tasks.cmd test
```

Результаты:

- `reports/report.html` — HTML-отчёт pytest;
- `reports/coverage/index.html` — покрытие.

### Стиль

```powershell
.\tasks.cmd lint
```

### Проверка Docker-окружения

```powershell
docker compose ps
docker compose --profile test run -T --rm tests
```

Если команда требует TTY в неинтерактивном окружении, используется `-T` после
`run`.

Не использовать `docker compose config` в открытом CI/agent-выводе: команда
разворачивает значения из `.env` и может напечатать секреты. Для диагностики
сервисов использовать `docker compose config --services` или обезличенный вывод.

## 5. Работа с внешними интеграциями

Live-пробы запускаются только явно и только с локальными credentials.
Обычный CI должен работать без них.

Перед probe агент фиксирует:

- какие переменные окружения нужны;
- какой запрос будет отправлен;
- какой расход или платёж возможен;
- какие данные будут сохранены после redaction;
- условия `go` и `stop`.

После probe обновляются:

- фактический контракт интеграции;
- decision record;
- требования и состояние фазы;
- тестовые fixtures без секретов и PII.

## 6. Итог работы агента

Финальный отчёт должен содержать:

```text
Изменения:
- ...

Проверки:
- команда → результат

Planning:
- выполненные требования;
- обновлённый STATE/PLAN/SUMMARY;

Ограничения:
- пропущенные проверки;
- необходимые credentials;
- известные риски.
```

Нельзя заявлять, что проверка прошла, если команда фактически не запускалась.

## Definition of Done

Задача готова, когда:

- код соответствует `AGENTS.md`;
- требования и активный план не расходятся с реализацией;
- добавлены или обновлены тесты для изменённого поведения;
- `demo`, targeted tests или полный test suite дают воспроизводимый результат;
- lint чистый;
- секреты и PII не добавлены;
- `STATE.md` и `SUMMARY.md` обновлены, если завершён planning-этап.
