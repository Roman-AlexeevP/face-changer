# Design: mvp-001-core-flow

Технические решения для изменения `mvp-001-core-flow`. Общая картина —
`docs/architecture.md`.

## Goals

- Сквозной путь «фото → видео» за один день после подключения движка.
- Возможность запустить весь путь без Higgsfield (`ENGINE=mock`) и без
  оплаты (`PAYMENT_PROVIDER=stub`).
- Ноль компонентов инфраструктуры сверх Postgres.

## Non-goals

Масштабирование, горизонтальный воркер-пул, повторные платежи, очередь с
приоритетами.

## Decisions

### D1. Очередь на PostgreSQL, без брокера

`SELECT ... FOR UPDATE SKIP LOCKED` + `status` + `next_attempt_at`.

**Почему:** один компонент меньше, транзакционность с бизнес-данными
бесплатно, отладка — обычным SQL. На 5–20 задачах в час разница с Celery
неизмерима.

**Альтернативы:** Celery/Redis (лишний сервис), arq (лишний Redis),
in-process `asyncio.Queue` (теряется при рестарте).

**Когда пересмотреть:** больше двух воркеров или нужен приоритет/отмена.

### D2. Два процесса, одна кодовая база

`bot` и `worker` — разные entrypoint'ы, общий пакет `app`.

**Почему:** рестарт бота не убивает идущие генерации, а падение воркера не
блокирует приём сообщений. Изоляция без микросервисов.

**Альтернатива:** один процесс с фоновой задачей — дешевле, но рестарт ради
деплоя обрывает заказы.

### D3. Статусы только через `order_service.transition()`

Разрешённые переходы — таблица в коде, всё остальное — исключение.

**Почему:** деньги и возвраты должны иметь одно место, где их можно
проверить. Прямая запись статуса — главный источник двойных возвратов.

### D4. `idempotency_key = order_id:attempt`

`UNIQUE` в БД, передаётся в движок, если он поддерживает.

**Почему:** рестарт воркера — штатная ситуация. Без ключа повторный submit
создаёт вторую генерацию и второй расход кредитов.

### D5. Polling, не webhook

**Почему:** решение заказчика. Не требует публичного HTTPS и стабильного
домена на этапе проверки. Интерфейс `VideoEngine` уже содержит `poll`;
добавление `parse_webhook` — отдельное изменение без ломки контракта.

**Цена:** задержка до интервала опроса и лишние запросы. При 3–5 секундах
интервала — несущественно.

**Когда пересмотреть:** при 50+ одновременных задачах или требовании к
секундной точности.

### D6. Шаблон — папка + запись в БД, синхронизация при старте

**Почему:** контент меняется чаще кода. Промпт правится в YAML и
применяется рестартом, без релиза.

**Ограничение:** изменение промпта во время работы не подхватывается — это
приемлемо для MVP.

### D7. Оплата-заглушка как полноценный провайдер

`stub.py` реализует тот же `PaymentProvider`, что и будущая ЮKassa, включая
`refund`.

**Почему:** путь «оплата → кредиты → возврат» проверяется целиком, а замена
на ЮKassa — это один файл и одна переменная окружения.

### D8. Хранение файлов на локальном диске

**Почему:** результат сразу уходит в Telegram, фото живёт минуты. S3 не даёт
ничего, кроме задержки и настройки.

**Цена:** нельзя масштабировать воркер на несколько машин. Приемлемо до
нескольких сотен заказов в день.

### D9. Результат не хранится, хранится `file_id`

**Почему:** Telegram — бесплатный CDN. Повторная отправка по `file_id` не
требует файла.

### D10. Один воркер, последовательная обработка с ограничением параллелизма

`WORKER_CONCURRENCY=2` — две задачи одновременно.

**Почему:** API имеет лимиты на параллельные задачи, а очередь из 2 задач
даёт предсказуемое время ответа. Конкурентность — параметр конфигурации, не
кода.

## Data model

См. `docs/architecture.md` §5. Ключевые ограничения:

- `orders.payment_id UNIQUE`
- `jobs.idempotency_key UNIQUE`
- `templates.key UNIQUE`
- индекс `jobs(status, next_attempt_at)`

## Sequence (успешный путь)

```
User  → Bot: фото
Bot   → PG: order(status=queued), job(new)
Bot   → User: «принято»
Worker→ PG: pick (SKIP LOCKED), job(running)
Worker→ Engine: ensure_asset(template)
Worker→ Engine: submit(spec) → request_id
Worker→ Engine: poll × N
Engine→ Worker: completed + URL
Worker→ User: sendVideo
Worker→ PG: order(delivered), job(done), cleanup
```

## Risks

| Риск | Вероятность | Митигация |
|---|---|---|
| Качество Genjutsu не подходит | средняя | этап 0 до кода бота |
| API недоступен из РФ | средняя | `VideoEngine` + альтернативный движок |
| Неизвестная цена кредитов | высокая | `ENGINE_CREDITS_HINT`, пересчёт после первого прогона |
| Расхождение схемы ответа движка с доку | средняя | `mock` фикстуры + сохранение `raw` в логах |
| Слив кредитов из-за бага в цикле | низкая | дневной лимит + kill switch |

## Rollout

1. Локально на `mock` — весь путь.
2. Один реальный заказ на `higgsfield` в тестовом чате.
3. Ограниченный доступ (5–10 пользователей), ручной контроль каждого заказа.
4. Открытая продажа.
